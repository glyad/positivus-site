# Positivus Blog v1.2.0 UX/UI and content-system design

- **Status:** Approved design specification
- **Date:** 2026-08-15
- **Target release:** v1.2.0
- **Visual direction:** Editorial Grid

## 1. Purpose

Positivus Blog is a bilingual, multi-author knowledge hub that turns the existing
marketing site into a durable learning destination. It serves business owners,
marketing leads, working practitioners, and specialists without making the
interface feel like a technical documentation portal.

The public article content is read-only and supplied by a CMS. Content is
validated and rendered into static pages during the build. The implementation
must preserve the existing dependency-free frontend, Positivus visual language,
English LTR behavior, and Hebrew RTL behavior.

The primary recurring conversion is newsletter signup. High-intent articles may
also contain one contextual consultation prompt when the article has a genuine
relationship to a Positivus service.

## 2. Goals

- Make useful marketing knowledge easy to discover through search, categories,
  tags, authors, series, filters, and related content.
- Give every author a credible primary profile and support co-authored and
  expert-reviewed work.
- Provide crawlable, fast, accessible static pages from replaceable CMS content.
- Keep global site search distinct from the deeper blog-only search.
- Support independently edited English and Hebrew content without silently
  mixing languages.
- Preserve the high-contrast, playful Positivus identity while improving
  long-form reading comfort.
- Define reliable empty, failure, missing-translation, and invalid-content
  behavior before implementation.

## 3. Non-goals for v1.2.0

- Selecting or provisioning a specific CMS vendor.
- Building a CMS administration interface.
- Real accounts, sessions, or persistent public comments.
- Comment replies, reactions, editing, deletion, moderation, reporting, spam
  protection, privacy controls, or comment-specific localization.
- Personal feeds, bookmarks, saved searches, paywalls, or algorithmic
  personalization.
- A live newsletter, consultation, or analytics provider integration.
- Replacing the existing authentication prototype with production
  authentication.

## 4. Experience principles

### 4.1 Editorial clarity

The composition uses strong headlines, generous whitespace, a restrained
reading column, and concise metadata. Lime highlights priority and interaction;
it must not become a large decorative background behind long text.

### 4.2 Progressive discovery

Visitors can begin with a featured story or topic, narrow results with filters,
follow an author or series, and continue through related articles. Discovery
controls must remain understandable without requiring a search query.

### 4.3 Visible provenance

Articles expose authorship, publication date, last-edited date, level, format,
reading time, and optional reviewer or correction information. Exact dates are
available wherever relative phrasing might be ambiguous.

### 4.4 Honest prototypes

Any interaction without a production backend must say so. The comment composer
must never imply that a comment was publicly saved, moderated, or delivered.

### 4.5 Visual-system application

The Blog extends the existing Positivus system instead of introducing a separate
publication brand:

- Electric lime `#B9FF66` marks selected topics, featured editorial moments,
  success, focus emphasis, and primary conversion accents.
- Dark ink `#191A23` provides primary text and high-emphasis controls; white and
  soft grey `#F3F3F3` provide the main reading and card surfaces.
- Space Grotesk remains the primary typeface. Display headings retain its bold,
  compact personality, while article body copy uses a comfortable 16–18px size,
  approximately 1.6 line height, and a maximum measure near 70 characters.
- Section labels may use the existing black-on-lime highlight treatment, but
  long article headings remain on an uncluttered surface.
- Featured and standard editorial cards use the established outlined surfaces,
  generous rounded corners, and hard dark shadow. Dense controls such as chips,
  inputs, and filters use smaller radii so content cards preserve their visual
  priority.
- Article cards can use white, grey, lime, or dark variants, but every variant
  must preserve readable metadata, consistent information order, and compliant
  contrast.
- Illustrations, portraits, and editorial imagery remain external assets. They
  are not replaced with emoji, font glyphs, CSS drawings, or approximate inline
  artwork.
- Hover treatment may shift or lift an outlined surface slightly; focus remains
  a stable, clearly visible outline and never depends on movement.

## 5. Information architecture

Route patterns below omit the locale strategy. Implementation must give every
localized article a distinct crawlable URL and reciprocal `hreflang` links while
retaining the existing language preference behavior.

| Route pattern | Purpose |
| --- | --- |
| `/blog/` | Blog home and primary editorial landing. |
| `/blog/search/?q=...` | Blog-only results with shareable filters and sorting. |
| `/blog/category/<slug>/` | Stable primary-category landing. |
| `/blog/tag/<slug>/` | Governed tag archive. |
| `/blog/series/<slug>/` | Ordered series or learning-path landing. |
| `/blog/authors/` | Multi-author directory. |
| `/blog/authors/<slug>/` | Main author profile and archive. |
| `/blog/<article-slug>/` | Article detail page. |

Published URL changes require an explicit redirect record. A localized record
may use a localized slug, but it retains the same CMS identity as its
translations.

## 6. Shared navigation and two-search model

### 6.1 Global search

The shared site header keeps the existing Request a quote action and adds a
compact lime search trigger. Activating it opens a full-width search overlay and
moves focus to the query field.

Global search covers:

- Site pages.
- Services.
- Case studies.
- Blog articles.
- Authors.

Results are grouped by source type. An empty query presents curated topics and
popular resources, not search history. No-results guidance includes spelling,
related topics, relevant services, and a route to the Blog. Escape closes the
overlay and returns focus to the trigger.

On mobile, Search Positivus and Request a quote both remain available from the
menu. The search overlay becomes a full-screen dialog with the same focus and
keyboard behavior.

### 6.2 Blog-only search

Blog search appears only on blog pages, beginning in the Blog Home hero. It
indexes article title, summary, content, authors, categories, and tags and can be
combined with blog filters.

When a query exists, relevance is the default sort. Without a query, newest is
the default. Search and filter state is represented in the URL so a result view
can be bookmarked, shared, and restored.

## 7. Page system

### 7.1 Blog Home

The Editorial Grid direction defines the landing page:

1. Knowledge Hub hero with blog-only search and primary topic chips.
2. One featured guide with strong artwork, summary, author, date, level, format,
   and reading time.
3. Latest Insights card grid.
4. Optional popular or evergreen collection.
5. Author discovery strip.
6. Governed tag cloud.
7. Newsletter conversion panel.

The feature hierarchy must remain evident when images are unavailable. Editorial
settings select the lead story and ordered collections; deterministic recency
rules provide a fallback.

### 7.2 Browse and search results

The page contains a result summary, active-filter chips, sorting, filter panel,
article cards, and accessible numbered pagination. It shows 12 items per page
and never uses infinite scroll.

Desktop uses a compact panel beside the results. Mobile uses a modal or drawer
with an active-filter count, Apply and Clear actions, predictable focus, and
restoration to the invoking control.

### 7.3 Category landing

A category landing explains the discipline, presents a featured entry, exposes
relevant formats and levels, and lists the remaining articles. Categories are
few, stable, and suitable for primary navigation.

### 7.4 Tag archive

A tag archive explains the governed topic when descriptive copy exists and
lists all matching published articles. It links back to the alphabetical tag
index and relevant primary categories.

### 7.5 Series or learning path

A series page describes the outcome, audience, level, estimated total reading
time, and ordered entries. Article pages show previous and next series entries.

### 7.6 Authors directory

The directory supports browsing by name and expertise. Each card includes a
portrait, role, concise biography, expertise tags, and published-content count.

### 7.7 Author profile

The primary author page includes:

- Portrait, name, role, biography, expertise, credentials, and optional
  professional links.
- Article, guide, or series counts and relevant experience.
- Featured work.
- Latest archive and topics.
- Optional reviewed-content attribution.

It does not include follower counts, personal feeds, or social-graph behavior.
Newsletter subscription follows the publication, not individual authors.

### 7.8 Article page

The article layout includes:

1. Breadcrumbs.
2. Primary category and level.
3. Title and editorial deck.
4. Primary author, co-authors, optional reviewer, publication date, last-edited
   date, format, and reading time.
5. Hero media.
6. Main reading column with a sticky desktop table of contents.
7. Copy-link and print actions.
8. Structured content blocks.
9. Tags, citations, correction note, and author attribution.
10. Optional contextual consultation prompt.
11. Related articles and series navigation.
12. Newsletter panel.
13. UI-only comment prototype.

On compact screens, the table of contents becomes a collapsible section before
the article body.

## 8. Taxonomy and filtering

### 8.1 Primary categories

Every article has exactly one primary category:

1. Strategy & Growth.
2. SEO.
3. Paid Media.
4. Content & Creative.
5. Social Media.
6. Email & Lifecycle.
7. Analytics & Optimization.

Category labels, descriptions, slugs, artwork, navigation order, and metadata
are localized and governed.

### 8.2 Multiple tags

Articles can have multiple tags, with an editorial maximum of five. Tags come
from a governed collection instead of free-form entry. Each tag has a canonical
identity, localized label and slug, optional description, and active or retired
status. Retired tags require a replacement or redirect where appropriate.

### 8.3 Additional dimensions

- Audience: leaders, practitioners, specialists; multi-select.
- Level: beginner, intermediate, or advanced; exactly one.
- Format: guide, how-to, framework, checklist, case analysis, opinion, or
  industry update; exactly one.
- Author: primary author and optional co-authors.
- Reviewer: optional.
- Series or learning path: optional.
- Reading duration: computed and filterable ranges.
- Publication and last-edited dates.
- Featured status and optional related service.

The user-facing filters are category, format, audience, level, author, reading
duration, and publication date. Tags are navigable through cards, tag pages,
search, and the tag cloud.

### 8.4 Tag cloud

The tag cloud appears on Blog Home and Browse. Frequency may influence visual
weight, but size or color is never the only representation: every entry exposes
an exact published-article count. An alphabetical presentation is available for
predictable scanning and assistive technology.

The mobile cloud is collapsible. Counts are locale-specific and include only
articles that are published and available in the current language.

### 8.5 Related-content priority

Related articles are selected in this order:

1. Explicit editorial selection.
2. Same series.
3. Shared category and tags.
4. Shared audience and level.

Automatic selections exclude the current article, unpublished content, and
articles unavailable in the current language.

## 9. CMS content contract

### 9.1 Content types

| Type | Responsibilities |
| --- | --- |
| Article | Identity, locale, slugs, content, taxonomy, authorship, dates, imagery, related content, conversion, and SEO. |
| Author | Identity, locale, name, role, biography, portrait, expertise, credentials, professional links, and feature status. |
| Category | Identity, locale, name, slug, description, artwork, navigation order, and SEO. |
| Tag | Identity, locale, label, slug, description, lifecycle state, and replacement. |
| Series | Identity, locale, title, description, artwork, audience, level, ordered entries, and SEO. |
| Redirect | Locale, old path, replacement path, status code, and reason. |
| Blog settings | Featured article, ordered collections, author highlights, popular resources, newsletter copy, and default metadata. |

### 9.2 Article fields

An article includes:

- Stable identity, locale, status, slug, title, editorial deck, short summary,
  and structured body.
- Primary category, up to five tags, audiences, level, and format.
- Primary author, optional co-authors, and optional reviewer.
- Optional series and order.
- Hero media, alt text or decorative designation, caption, and social crop.
- Publication date and last-edited date.
- Computed reading time with an optional editorial override.
- Featured flags, manually related articles, and optional service relationship.
- Optional citations, correction note, and downloadable resources.
- Search title and summary overrides when editorially necessary.
- SEO title, description, canonical override, indexing directive, and social
  metadata.

### 9.3 Publication lifecycle

The adapter recognizes draft, scheduled, published, preview, and archived
records. Only valid published records enter the public build or search indexes.
Preview records are available only through a protected preview deployment.
Archived or renamed public URLs require an explicit redirect or a documented
withdrawal response.

### 9.4 Structured article blocks

Top-level article composition uses structured blocks rather than one unrestricted
HTML field. Rich text remains available within appropriate blocks.

Supported blocks are:

- Introduction and key takeaways.
- Heading and rich-text section.
- Image or figure with caption and attribution.
- Quotation or testimonial.
- Statistic or highlighted insight.
- Checklist and numbered steps.
- Comparison or data table.
- Media and downloadable resource.
- Citation and references group.
- Informational, warning, or expert callout.
- FAQ group.
- Contextual consultation prompt.

Validation enforces a logical heading hierarchy, safe links, required media
accessibility fields, valid references, and supported block combinations.

## 10. CMS delivery architecture

The provider-specific adapter runs during the build and produces normalized,
validated content. The browser never contacts the CMS and never receives CMS
credentials.

```text
CMS content
  -> provider adapter
  -> schema and relationship validation
  -> normalized localized records
  -> static pages + global index + blog index + RSS + sitemaps + metadata
  -> existing GitHub build, checks, packaging, and deployment flow
```

CMS publishing events trigger the GitHub workflow through a webhook. A failed
content import or validation stops the new deployment and leaves the current
production build online. Error output identifies the record, locale, field, and
expected correction without exposing credentials.

The global index contains lightweight entries for site pages, services, case
studies, authors, and articles. The blog index contains article text and the full
filter metadata. Both indexes are static, versioned build artifacts.

## 11. Dates and editorial transparency

The article header shows Published and Last edited as distinct values. The
last-edited label is displayed when the CMS value differs materially from the
publication date. Cards show the publication date where space permits; results
and archives always expose it in structured metadata.

Dates use localized, unambiguous absolute formatting. Machine-readable
`datePublished` and `dateModified` values use valid ISO timestamps. An optional
correction note explains material post-publication changes without replacing the
last-edited value.

## 12. Comment prototype

The article discussion area demonstrates the intended entry point without a
production community system.

- Signed-out users see a Sign in to comment action leading to the existing fake
  authentication journey.
- Demo signed-in users see a labelled text area and submit action.
- Valid submission adds the comment to the current in-memory page session only.
- A persistent notice says that comments are a demonstration and are neither
  published nor stored.
- Representative static comments may illustrate the final reading treatment.
- Refreshing or leaving the page removes the submitted demonstration comment.

The prototype must not write comment text to local storage, a URL, logs, a
network request, or generated artifacts. It does not promise moderation,
delivery, account identity, or public visibility.

## 13. Conversion design

### 13.1 Newsletter

Newsletter signup is the primary recurring blog conversion. It appears on Blog
Home and near the end of article and archive experiences without interrupting
reading. Repeated instances on one page are avoided. Until a production endpoint
is selected, the control follows the existing transparent prototype behavior.

### 13.2 Consultation

A consultation prompt appears only when an editor explicitly relates an article
to a Positivus service. The prompt explains the relationship and provides one
clear action. It does not obscure article content or appear as a generic popup.

## 14. Localization and bidirectionality

English and Hebrew versions share a stable CMS identity but can independently
define title, summary, slug, body, metadata, imagery, and taxonomy labels. A
missing translation produces a dedicated availability message and link to the
available language; the page never silently inserts paragraphs or cards from a
different language.

Layout uses logical properties and mirrors navigation, filter placement, table
of contents, directional controls, and reading flow in RTL. Logos, photographs,
provider marks, and non-directional artwork are not mirrored. Directional
illustrations are mirrored only when their meaning requires it.

Names, URLs, dates, codes, and mixed-direction metadata use appropriate bidirectional
isolation. Search indexes, tag counts, related content, RSS, sitemaps, and
structured metadata are locale-specific.

Comment-specific translated states and specialized RTL discussion behavior are
outside v1.2.0; the prototype remains clearly identified as limited.

## 15. Responsive behavior

- The main content shell follows the existing Positivus width and spacing
  rhythm.
- Editorial cards render in three, two, and one column according to available
  width.
- The desktop filter panel becomes a focused mobile drawer.
- The sticky article table of contents becomes a collapsible section.
- Author identity and article metadata wrap without truncating essential
  information.
- Tables use a labelled overflow container or a compact semantic alternative.
- The tag cloud can collapse on compact screens without hiding the alphabetical
  route.
- Touch targets remain large enough at the narrowest supported viewport.

## 16. Accessibility requirements

- Semantic header, navigation, main, article, aside, section, footer, list, and
  form structures.
- One page-level heading and a validated article heading hierarchy.
- Skip links for primary navigation, filters, results, and article content where
  applicable.
- Visible focus indicators and fully keyboard-operable search, filters, dialogs,
  pagination, table of contents, share actions, and prototype forms.
- Accessible names and states for icon-only controls.
- Focus containment and restoration for search overlays and mobile filter
  dialogs; Escape closes dismissible layers.
- Search result counts, validation, and status changes announced through
  appropriate live regions.
- Exact counts accompanying tag-cloud visual weight.
- Alt text or an explicit decorative designation for all media.
- Sufficient text, control, border, error, and focus contrast.
- Reflow and text resizing without lost content or two-dimensional page
  scrolling, except for intentionally labelled data tables.
- Reduced-motion behavior for transitions and loading indicators.
- No information communicated by color, position, or animation alone.

## 17. System states

Every applicable page or component defines:

- Initial and populated content.
- Loading or build-time placeholder treatment.
- No query and no results.
- Active filters with zero results.
- Missing translation.
- Missing or withdrawn content.
- Invalid or expired preview.
- Broken referenced content caught before deployment.
- Search-index unavailable or incompatible.
- Image unavailable.
- Newsletter or consultation prototype success and failure.
- Comment signed-out, signed-in, empty, invalid, submitting, demonstration
  success, and session-reset behavior.

Recovery actions are specific: clear filters, change language, browse a
category, request a valid preview, return to Blog Home, or contact the editorial
team. Generic dead ends are not acceptable.

## 18. SEO, feeds, and sharing

The generated output includes:

- Unique localized titles and descriptions.
- Canonical URLs and reciprocal `hreflang` relationships.
- Open Graph and social-card metadata.
- `Article`, `Person`, `BreadcrumbList`, and appropriate organization structured
  data.
- Publication and modification timestamps.
- Locale-aware XML sitemaps.
- RSS feeds for all articles, primary categories, and authors.
- Stable share and print URLs that omit transient interface state.

Drafts, previews, private build reports, and prototype comments are excluded from
public indexes, feeds, sitemaps, and structured data.

## 19. Measurement hooks

The UI exposes vendor-neutral, privacy-conscious hooks for:

- Global and blog search submission.
- Filter application and clearing.
- Result selection.
- Article and author navigation.
- Tag, category, and series navigation.
- Newsletter and consultation actions.
- Copy-link and print actions.

No analytics provider or identity linkage is introduced in v1.2.0. Search terms
and prototype comments are not persisted by the application.

## 20. Verification and acceptance criteria

### 20.1 Content validation

- Required fields, supported blocks, dates, slugs, relationships, localized
  references, and media accessibility fields are validated before output.
- Duplicate localized routes and unresolved redirects fail the build.
- Only valid published records appear in public pages and indexes.
- Tag counts, author counts, reading time, pagination totals, feeds, and sitemap
  entries are deterministic.

### 20.2 Functional behavior

- Every approved page route is generated from representative CMS-agnostic mock
  data.
- Global search and blog search remain separate and return only their intended
  content types.
- Filter combinations, sorting, URL restoration, and 12-item numbered
  pagination behave consistently.
- Related content follows the approved editorial and automatic priority.
- The comment prototype performs no network or durable storage operation.
- Newsletter and consultation prototypes accurately state their limitations.

### 20.3 Localization and accessibility

- English and Hebrew pages provide equivalent editorial and navigation
  capabilities where translations exist.
- Missing translations display the approved availability state.
- Automated checks cover localization completeness, document direction,
  metadata, labels, landmark structure, focus-related attributes, and build
  output.
- Manual QA covers keyboard navigation, screen-reader announcements, zoom,
  reflow, reduced motion, desktop, tablet, compact mobile, LTR, and RTL.

### 20.4 Visual QA

Visual evidence covers Blog Home, results, article, authors directory, author
profile, category, tag, series, global search, blog filters, empty results,
missing translation, and comment prototype states. Key screens are captured in
English and Hebrew at desktop and mobile widths.

### 20.5 Repository and release quality

- The public frontend introduces no unapproved runtime dependency.
- `npm run check` passes before the feature pull request.
- `npm run release:dry-run` passes before the develop-to-main release pull
  request.
- User-visible changes update the changelog and synchronized version metadata.
- Feature, release, and synchronization pull requests use regular merge commits.

## 21. Deferred decisions

The implementation plan may define adapter interfaces and representative mock
data, but these external choices remain intentionally deferred:

- CMS vendor and credential provisioning.
- Production newsletter, consultation, and analytics providers.
- Production authentication and comment storage architecture.
- Community governance, moderation, abuse prevention, legal, and privacy policy.

Any future decision to persist user comments reopens those production safeguards
as required scope rather than treating them as optional enhancements.
